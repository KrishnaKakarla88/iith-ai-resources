## Harder / real-interview-style

Grounded in current (2025-2026) Python interview practice for AI-adjacent roles ([techinterview.org](https://www.techinterview.org/post/3233474450/python-interview-questions-2025-generators-decorators-async-await-type-hints-dataclasses-concurrency-gil-memory-management/), [DataCamp](https://www.datacamp.com/blog/top-python-interview-questions-and-answers), [dev.to 40 Python questions](https://dev.to/finalroundai/40-python-interview-questions-for-2025-how-many-can-you-answer-9k6)) and this repo's own patterns ([[python-data-types-and-mutability]], [[lists-tuples-sets-dicts]], [[functions-args-kwargs]]).

#### Mutability and default arguments

- **Q: A function `def add_item(item, bucket=[])` is used across a codebase to accumulate items into a "fresh" list each call. What actually happens, and why?**
  A: Default argument values are evaluated exactly once, at function *definition* time, not on every call — so every call that doesn't pass its own `bucket` shares the *same* list object across all calls, and items silently accumulate across unrelated invocations instead of starting empty each time. The fix is `def add_item(item, bucket=None): bucket = bucket if bucket is not None else []` — evaluated fresh inside the function body, on every call.
- **Q: You pass a list into a function, the function reassigns the parameter name to a new list inside its body, and the caller's original list is unchanged. But if the function instead calls `.append()` on it, the caller's list *does* change. Why the difference?**
  A: Reassignment (`bucket = bucket + [item]` or `bucket = new_list`) rebinds the local name to point at a new object — it never touches the object the caller's variable still references. `.append()` mutates the object itself in place, and since both the caller's name and the parameter name point at the same object, the caller sees the change. This is the core distinction between rebinding a reference and mutating the referent, and it trips people who think "passed by reference" and "passed by value" fully describe Python's actual pass-by-object-reference semantics.
- **Q: Why would you deliberately choose a tuple over a list for a function's return value representing, say, `(status, message)`?**
  A: Immutability signals intent — a tuple communicates "this is a fixed, complete record, not a collection you should append to," and it's also hashable, so it can be used as a dict key or put in a set (a list can't). It's a smaller, faster fixed-size container, which matters less for correctness than for the API contract it communicates to whoever reads the calling code.

#### Collections and choosing the right one

- **Q: A junior engineer stores thousands of "already-processed ticket IDs" in a list and checks membership with `if ticket_id in processed`. What's the problem at scale, and what should replace it?**
  A: `in` on a list is O(n) — it scans linearly, so the check gets slower as the list grows, and doing this per-ticket across thousands of tickets turns into O(n²) total work. A `set` gives O(1) average-case membership checks via hashing, which is the entire reason it exists as a distinct type from a list — this is a very common "do you understand the collections you reach for, not just their syntax" interview probe.
- **Q: When would a dict-of-lists be the wrong structure, and a list-of-dicts the right one — or vice versa?**
  A: A dict-of-lists suits fast lookup by a stable key (e.g. `tickets_by_customer_id[cust_id]` — you always know the key you want). A list-of-dicts suits cases where you need to iterate everything, filter/sort by different fields at different times, or the "key" isn't unique/stable (e.g. a feed of events you scan and filter by varying criteria). Picking based on "which operation happens most often" — lookup-by-key vs. iterate-and-filter — is the actual decision, not a stylistic preference.
- **Q: Why can a dict's iteration order be relied on in modern Python, and why might relying on it still be a design smell?**
  A: CPython 3.7+ guarantees insertion-order iteration for dicts as a language-level guarantee, not an implementation detail — so it's safe to depend on. It's still often a smell because code that silently depends on insertion order to be *correct* (rather than just for stable display) usually means a list or an explicit sort would communicate the actual requirement more clearly than an incidental property of a dict.

#### Functions, *args/**kwargs, and scope

- **Q: A wrapper function is meant to forward to any underlying function signature: `def wrapper(*args, **kwargs): return fn(*args, **kwargs)`. What breaks if you instead write `def wrapper(args, kwargs)`?**
  A: Without the `*`/`**` unpacking, `wrapper` only accepts exactly two positional arguments named `args` and `kwargs` — calling it the way the real function is normally called (`wrapper(a, b, key=c)`) raises a `TypeError` for too many arguments. `*args`/`**kwargs` collect an arbitrary number of positional/keyword arguments into a tuple/dict so the wrapper can genuinely forward *any* call shape — this is the mechanism every decorator in the stack (retry, circuit-breaker, tracing) depends on to stay generic across the functions it wraps.
- **Q: Why does a closure that captures a loop variable often not do what people expect — e.g. building a list of functions in a `for` loop, each meant to "remember" its own `i`?**
  A: A closure captures the *variable*, not its value at the time the closure was created — so all closures built inside the loop share the same `i`, and by the time any of them actually run, `i` holds its final value from the last iteration. The fix is binding the current value as a default argument (`lambda i=i: ...`) or via a factory function, forcing evaluation at closure-creation time instead of call time — the same "evaluated once vs. evaluated per-call" distinction that makes the default-mutable-argument bug (above) dangerous.
- **Q: What's actually different between a positional-only parameter, a keyword-only parameter, and a regular parameter — and why would an API deliberately restrict which one callers can use?**
  A: Regular parameters can be passed either way; `def f(a, /, b, *, c)` forces `a` positional-only, `c` keyword-only, `b` either. Restricting matters for API stability — a keyword-only parameter can be reordered relative to others in a later version without breaking callers, while a positional-only parameter frees the *name* to change without breaking callers who never used the name. This shows up in library and SDK design (including tool-schema functions in this stack) more than in everyday application code.
